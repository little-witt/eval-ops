# FORGE / ACEval 项目评测与自迭代总结

> 适用对象：希望快速了解 FORGE / ACEval 产品价值、评测模型和迭代机制的研发、产品与评测人员  
> 当前边界：基于现有 V2 / P0 实现；完整 V3 Path IR、逐事件 hash chain 和更广泛的真实业务验收仍在推进

## 1. 一句话说明项目

FORGE 是一个本地优先的 Skill 评测与进化桌面工具，ACEval 是它的规则化控制 Kernel。

它解决的不是“给 Skill 跑一个分数”，而是：

> 用真实 Agent 执行 Case，回收并校验证据，区分 Skill 问题、执行波动与环境/评测基础设施问题；无法可靠归因时保留未知，再通过受控修改和回归评测决定新版本能否替代旧版本。

完整闭环如下：

```text
Skill / 目标 / 标准
  → 评测设计与 EvalPack
  → Case 与语义路径
  → 真实 Agent 执行
  → Trace 与证据回收
  → 多维评分与失败归因
  → 用户批准修改范围
  → 多文件 Candidate
  → Champion / Challenger 对比
  → 晋升、拒绝或安全停止
```

### 1.1 先分清三个模型角色

| 角色 | 主要工作 | 权限边界 |
|---|---|---|
| 执行 Agent | 在真实环境中完成 Case，产生回复、工具调用和产物 | 不能修改评测契约和 Oracle |
| 分析模型 | 做开放语义评分，提出带证据引用的归因假设 | 不能推翻硬事实或决定晋升 |
| 修改模型 | 在用户批准的文件范围内生成候选内容 | 不能扩大修改范围或直接宣布发布成功 |

三个角色在部署上可以使用同类模型，但实验上必须区分身份、输入和权限，避免同一个上下文既执行、又看隐藏答案、又给自己判分。

常用术语：Fixture 是测试数据或仓库；Oracle 是可信的正确标准；Grader 是执行判定的评分器；Trace 是原始执行轨迹；Evidence 是从 Trace、状态和产物中得到的可验证证据；source ref 是结论对应的 Skill 文件位置。

## 2. 项目亮点、难点和解决方式

| 亮点或难点 | 核心问题 | 当前解决方式 |
|---|---|---|
| 从评测做到进化闭环 | 常见评测只能跑 Case、出分数，不能安全修改 Skill | 串起评测设计、真实执行、Trace、归因、候选修改、回归和版本晋升 |
| 防止模型自证 | 如果模型自己出题、打分、修改并宣布成功，结果容易过拟合 | 模型负责语义判断、根因假设和候选内容；Kernel 负责证据资格、硬门、权限、回归、晋升和停止 |
| 处理 Agent 随机性 | 一次成功不代表稳定成功 | 同一 Case 支持多次 Attempt，记录 `pass@k`、`pass^k` 和稳定通过状态 |
| 区分 Skill 问题和环境问题 | 网络、工具、权限或日志异常容易被误判为 Skill 失败 | 先检查 Evidence Validity；证据无效时返回 `not_evaluable`，不授权修改 |
| Skill 没有清晰代码模块边界 | 自然语言、脚本、配置和模板可能共同决定行为 | 建立“目标 → 能力/义务 → Case/路径 → source ref → 修改范围”的追溯关系 |
| 多文件修改容易引入回归 | 修复一个 Case 可能破坏原有稳定能力 | 使用文件白名单、精确替换、静态检查、稳定通过保护集和 Champion / Challenger 对比 |
| Agent 可能存在多条正确路径 | 固定唯一工具序列会误杀合理实现 | 使用 required、recommended、alternative、forbidden 和局部顺序描述语义路径 |
| 长链路容易中断 | 远程 Session、日志、模型分析、Git 发布都可能失败 | 分阶段持久化、追加式事件、带 hash 的证据产物、可恢复分析和审计式 Git 回滚 |

项目真正的核心不是某个 Prompt，而是把不确定的模型行为放进一套相对确定、可审计、可回滚的工程控制面。

## 3. EvalPack、Case 和路径

### 3.1 EvalPack：一套可复用的考试包

EvalPack 用于冻结一套评测资产，通常包含：

- Case：具体测试任务；
- Fixture：测试输入、仓库或环境数据；
- Oracle / Grader：正确标准和评分方式；
- Path：关键行为和禁止行为；
- Schema：输入输出格式；
- Dev、Validation、Holdout 等测试分组。

用户可以提供自定义 EvalPack；没有时，系统根据 Skill、目标、标准和已有 Case 自动生成。subject commit、Case revision、Fixture、Grader、Schema 和关键环境 hash 等评测契约匹配时可以复用；其中任一关键变量变化，都需要重新校准或建立新的设计 revision，不能偷偷沿用旧总分。

EvalPack 是可修订、但每个 revision 一经用于比较就不可原地改写的版本化容器。一个 Case 可以对应一条或多条合法路径，一条公共路径规则也可以被多个 Case 复用。

### 3.2 Case：一道具体考题

例如：

> 给 Agent 一个包含空地区和退款金额的 CSV，要求正确汇总，不能漏掉空地区记录。

一个 Case 通常记录：

- 输入与测试环境；
- 预期结果或通过标准；
- 风险等级和测试目的；
- 对应能力、义务和 source ref；
- 执行路径和 Grader；
- Case revision、来源和内容 hash。

### 3.3 路径：关键行为契约

路径不是唯一正确的工具调用录像，而是对关键行为的约束。例如：

```text
required     必须读取真实 CSV
alternative 可以使用 Python，也可以使用表格工具
forbidden    不能编造缺失数据
recommended 最好解释空值处理方式
局部顺序     必须先获得授权，再执行写入
```

最终结果、安全、权限和强制业务步骤可以成为硬门；普通实现细节不默认强制。

### 3.4 它们如何生成

当前流程是：

1. 冻结 `SKILL.md`、脚本、配置、模板和引用资料；
2. 结合用户目标、标准和已有 Case，分析能力与风险；
3. 生成正常、边界、错误、恢复、权限和安全等测试义务；
4. 系统生成可追溯的 Case 草稿，模型可以补充语义场景和文案；
5. 根据 Skill 规则、测试义务和 Case 生成语义路径；
6. 检查来源、可执行性、Oracle 可信度和可观察性；
7. 用户确认后版本化冻结进 EvalPack，使执行和后续比较可复现。

目标架构是完整的“路径先于 Case”。当前已经具备能力图、风险规划、测试义务和路径约束，但完整 V3 Path IR 尚未全部落地，部分路径仍在 Case 生成后补齐。

## 4. 三层裁决模型

### 4.1 Attempt：判断一次执行

一次 Case 执行就是一个 Attempt。它回答：

- 本次证据是否完整；
- 最终结果是否正确；
- 关键步骤、安全和权限是否通过；
- 本次执行是 `pass`、`fail` 还是 `not_evaluable`。

Attempt 可以包含 Outcome、Procedure、Grounding、Runtime、Efficiency 等维度。维度分数可以形成摘要，但硬门失败时，其他高分不能把结果抵消为通过。

### 4.2 Case Aggregate：判断一个 Case 是否稳定

同一个 Case 可以执行多次，Case Aggregate 汇总这些 Attempt。

假设执行三次，结果为：

```text
pass、pass、fail
```

则观察成功率为 `2/3`，同时说明该能力存在波动。

在把观察成功率 `p` 当作单次成功概率、并近似假设各次运行独立同分布时，可以估算：

- `pass@k`：运行 k 次，至少成功一次的概率，表示“有没有机会完成”；
- `pass^k`：运行 k 次，全部成功的概率，表示“能不能稳定完成”。

例如估计单次成功概率为 80%，运行三次：

```text
pass@3 = 99.2%
pass^3 = 51.2%
```

这些是理论估计指标，不能代替实测结果。当前晋升门实际使用更严格的 `stable_pass`：在规定重复次数内全部通过，而不是只看一次成功或较高的 `pass@k`。

### 4.3 Candidate Comparison：判断修改能否取代旧版本

系统把当前稳定版本称为 Champion，把修改后的候选称为 Challenger。双方在同一套 Case、环境和 Grader 下进行配对比较。

Challenger 被接受至少需要满足：

- Case、评测契约和运行环境可直接比较；
- 双方证据有效；
- Challenger 没有硬门失败；
- 已稳定通过的 Case 没有退化；
- Challenger 达到重复运行要求；
- 配对平均收益达到最小提升门槛。

比较结果有三种：

- `accepted`：通过全部门禁，Challenger 晋升；
- `rejected`：出现确定性退化、硬门失败或收益不足，恢复 Champion；
- `inconclusive`：证据不足或上下文不可比，保留 Challenger 等待补证据。

例如原版本稳定通过 6/10 个 Case，新版本稳定通过 8/10 个；只有新增 2 个通过、原 6 个均未退化、双方环境和 Case revision 一致、重复运行达标，并且配对平均收益超过冻结阈值时，才可以晋升。阈值来自任务 Policy / 评测契约，不由分析模型临时决定。

## 5. 总分、修改审批和版本演进

### 5.1 总分如何得到

当前实现提供一个便于理解的摘要分：

```text
quality_score = 稳定通过的 Case 数 / 本轮参与分析的 Case 数
```

同一个 Case 无论有多少 Attempt，在分母里只算一次。证据无效的 Case 不能成为稳定通过，因此仍会压低该分数；已经按规则退休、不在本轮执行的 Case 不进入本轮分母，但继续进入回归保护清单。报告时应同时展示 Case 覆盖数、`not_evaluable` 数和稳定通过数，不能只展示 `quality_score`。

此外还有：

- Attempt 的各维度分和平均分；
- Case Aggregate 的成功率、稳定性、`pass@k` 和 `pass^k`；
- Candidate Comparison 的逐 Case 配对差异、维度差异和平均收益。

总分只是摘要，不是唯一裁决标准。例如总分从 80% 提升到 90%，但出现一个安全 Case 退化，Challenger 仍然会被拒绝。

### 5.2 谁决定是否接受模型修改

整个过程有三道权力边界：

1. 模型提出根因假设、修改建议和候选内容；
2. 用户批准具体修改范围，并授权候选进入 Git 分支和回归评测；
3. Kernel 根据真实回归结果决定是否具备晋升为 Champion 的资格。

模型没有直接写任意文件、绕过审批、决定晋升或宣布收敛的权限；Kernel 也不能替用户扩大写入范围。硬门不能被总分抵消，用户若改变目标或评测标准，应创建新的设计 revision，而不是在原比较中强行放行。

### 5.3 下一轮基于哪个版本继续修改

遵循 Champion 规则：

- Challenger 退化：候选被拒绝，通过可审计 Git revert 恢复 Champion 内容；下一轮基于恢复后的 Champion 修改；
- Challenger 提升并晋升：它成为新的 Champion；下一轮基于新 Champion 继续修改；
- 对比证据不足：既不接受也不拒绝，保留同一个 Challenger 等待补证据，不重新生成另一个补丁。

因此，系统不会在已知退化版本上继续叠加修改。

## 6. 一轮评测的最终结论如何产生

最终结论不是单纯让模型读完日志后自由总结，而是“规则化事实 + 受限语义判断”的组合。

### 6.1 系统先判断硬事实

Kernel 和 Grader 先检查：

- Session 是否真实完成；
- 环境、Skill commit、Fixture 和 Case revision 是否匹配；
- 日志和工具调用是否完整；
- 最终状态、产物、参数和禁止动作是否满足；
- 是否存在权限、安全或破坏性副作用问题。

网络异常、日志缺段、Fixture 错误或 Grader 异常会进入环境/证据问题，不直接记为 Skill 失败。

### 6.2 模型再处理开放语义

模型获得有界的：

- Case 和通过标准；
- 原始 Trace 与关键证据；
- Skill 原文、脚本和配置摘要；
- 能力图、路径和 source ref；
- 已确定的硬事实。

模型据此给出语义评分、跨 Case 根因假设和修改建议。硬事实会在模型输出后再次覆盖，模型不能把确定性失败改成通过，也不能把证据不足改成 Skill 问题。

### 6.3 bad case 如何归因

这里的 bad case 指“Case Aggregate 没有形成可信稳定通过”，不等同于“Skill 一定有错”。

| 观察结果 | 归因处理 | 是否允许修改 Skill |
|---|---|---|
| Session、日志、Fixture 或 Grader 无效 | `not_evaluable`，归为基础设施/证据问题 | 否 |
| 证据有效，明确发生网络、工具或权限故障 | 环境或依赖问题 | 否 |
| 同一契约下有时通过、有时失败 | 执行波动 / flaky，增加重复验证 | 暂不直接授权 |
| 证据有效，行为违反 Skill 明确要求，且能定位 source ref | Skill-attributed 候选问题 | 可以提出修改，仍需用户批准 |
| Skill 已明确要求，但执行 Agent 未遵循 | Agent 执行偏离，不能自动等同于 Skill 缺陷 | 视跨 Case 证据决定 |
| 多种原因冲突或证据置信度不足 | unknown / 人工复核 | 否 |

模型输出的是带证据引用的归因假设；Kernel 负责判断证据是否有资格支持修改，不宣称自己理解了唯一真实根因。多种原因可以同时保留，不能强制归成单一标签。

### 6.4 是否存在预设知识

系统有通用规则，但没有预设每个业务 Skill 的正确答案。

通用积累包括：

- 网络、超时、限流、命令不存在和工具失败等失败特征；
- 权限、安全、禁止副作用和证据完整性规则；
- EvalPack 中的 Oracle、Fixture 和 Grader；
- 当前 Skill 的原文、脚本、配置和 source ref。

具体业务知识必须来自用户标准、权威规范或经过校准的 EvalPack。被测 Skill 可以提供路径和能力线索，但不能单独证明自己正确。发生冲突时，用户/权威规范和独立 Oracle 优先；无法消解的冲突会阻断比较，而不是交给模型自由裁决。

## 7. 中断重试和幂等机制

系统持久化任务状态、追加式事件、Batch、Case、Session ID、Attempt、环境 hash 和分析产物，因此可以从最近的可信阶段恢复。

### 7.1 不同环节如何重试

| 中断位置 | 重试方式 |
|---|---|
| 远程 Session 已创建 | 使用原 Session ID 继续轮询和拉日志，不重新创建 |
| 部分 Case 因基础设施或传输失败 | 只重跑这些失败 Case，成功 Case 保持不变 |
| 日志拉取失败 | 继续拉取原 Session 的完整日志 |
| 本地模型分析失败 | 复用冻结 Trace，从失败阶段重新分析，不重跑远程 Case |
| 候选生成失败 | 保留分析与审批记录，重新生成候选，不覆盖旧产物 |
| Challenger 对比证据不足 | 保留相同 Challenger，补充证据后重新比较 |

有效证据下的业务 `fail` 不会为了挑出一次成功而自动重跑，它会直接进入分析和归因。基础设施失败或明确的证据恢复会创建新的 Attempt，旧 Attempt 仍保留在历史中，不会被覆盖。

### 7.2 如何保证幂等

主要依靠：

- `task + iteration + purpose + case` 的稳定身份；
- 请求 fingerprint 和冻结环境 hash；
- 唯一 Session ID、Attempt ID 和 Case revision；
- 原子写入和追加式事件；
- Candidate 的 parent hash 校验；
- Git 不可变 commit 和审计式 revert。

重复调用 dispatch 时，系统会优先读取持久化 Batch：运行中或成功的 Session 不重复创建，只有明确的基础设施/传输失败或显式证据恢复才产生新的 Attempt。

### 7.3 当前幂等边界

CATX 创建 Session 的接口没有原生幂等键。如果系统恰好在“远程 Session 已创建，但 Session ID 尚未持久化”之间崩溃，就无法确认远端是否创建成功。

对此系统选择 fail closed：拒绝自动再次创建；只有用户确认风险并明确重试后，才创建一个新的 Attempt。这样可能留下一个无法自动关联的孤立 Session，但不会静默重复执行可能带副作用的任务。

准确地说，系统追求的是“已有成功 Session 不自动重复”和“所有重试有历史”，不能保证远端 exactly-once。人工重试前应先检查 CATX 中是否存在孤立 Session；若 Case 有外部副作用，还需要确认环境能够隔离、回滚或接受重复执行风险。

## 8. Agent / Skill 评测的关键积累

1. **统一被测对象**：`EvaluationSubject` 同时覆盖 Skill 和 Agent，评测内核不依赖单一文件形式。
2. **稳定评测契约**：形成 Case、Attempt、Trace、Evidence、Grade、Aggregate、Comparison、Diagnosis 和 Convergence 等版本化对象。
3. **证据追溯链**：目标、义务、Case、路径、Session、证据、问题簇、修改和晋升可以互相追溯。
4. **失败归因体系**：区分 Skill、模型随机性、工具、环境、Fixture、Oracle、Grader 和日志问题。
5. **多维行为评测**：同时观察结果、过程、证据、运行状态、安全和成本。
6. **稳定性资产**：积累 Validation、Holdout、稳定通过保护集、失败签名和回归 Case。
7. **受控自迭代**：模型提出候选，用户控制授权，Kernel 控制发布质量和停止条件。

停止条件包括达到稳定目标、预算或最大轮次耗尽、连续多轮没有有效提升、重复相同问题形成循环、证据不足以及目标冲突。安全停止只表示在当前评测契约和预算内停止，不代表找到了全局最优 Skill。

## 9. 与主流方案的主要差异

| 方案类型 | 常见能力 | FORGE / ACEval 的补充 |
|---|---|---|
| Agent Eval / Trace 平台 | Trial、Trace、Grader 和可观测性 | 把失败证据继续连接到 Skill source ref、候选修改、Git 发布和回归晋升 |
| SWE-bench、τ-bench 等 Benchmark | 在固定任务集上比较 Agent | 面向具体业务 Skill 构建和沉淀评测资产，目标不是排行榜，而是安全改进当前对象 |
| GEPA、Prompt Optimizer、反思式优化 | 根据轨迹反思并生成新 Prompt | 模型没有 Oracle、归因、权限、晋升和停止权；候选必须通过确定性门禁 |
| 传统 CI / 自动化测试 | 精确断言和稳定回归 | 支持多种合法答案、语义路径、模型随机性、`not_evaluable` 和副作用安全 |
| “优化 Skill 的 Skill”脚本 | 快速重写 Prompt 或 `SKILL.md` | 支持完整资源树、最小语义 Diff、审批、不可变 Champion、回滚和跨轮问题追踪 |

核心差异可以概括为：

- 从结果评分升级为证据驱动的 Skill 生命周期管理；
- 从模型自治优化变成模型提议、用户授权、Kernel 裁决；
- 从单文件 Prompt 调优扩展到多文件、真实环境、回归保护和安全停止。

这更适合被描述为系统级组合和工程闭环创新，而不是声称发明了全新的基础算法。

## 10. 当前实现边界

当前工程已经实现桌面端、持久化 Kernel、真实远程 Trial、日志分页回收与完整性校验、分阶段分析、用户审批、多文件候选、Champion / Challenger 和本地 D2C 验证底座。日志缺失或校验失败时会返回 `not_evaluable`，不等同于已经具备完整可重放、防篡改的 EventJournal。

仍需继续推进：

- 完整的 V3 Path IR 和路径先行编译；
- 逐事件 hash chain 和可重放 EventJournal；
- 完整 Case / Suite 质量门和 Reference Run；
- AgentSubject 的通用候选发布 Adapter；
- 更多真实业务 Skill 的完整多轮远端验收与领域校准。

因此，当前可以宣称的是：项目已具备可信评测与受控自迭代的工程闭环；不能宣称已经解决所有业务 Oracle、覆盖所有 Agent 类型，或能找到全局最优 Skill。
